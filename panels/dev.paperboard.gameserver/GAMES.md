# Game modules

Minecraft Java, Terraria, Palworld and Team Fortress 2 are registered modules. Terraria uses a pinned publisher ZIP, stdin control, generated settings, a vault join password and offline backups. Minecraft retains its installers, launch arguments, readiness markers, console parsing, port names, tabs, Actions schemas and widgets. Terraria's `software: "tmodloader"` (phase 1b) is registered too: a pinned tModLoader GitHub release run on Origami's `dotnet-8` package, with a Mods tab over the Steam Workshop.

## Module contract

- `src/games/types.ts`: UI-safe `GameDefinition`, `GameOptions`, `GameFeatures`, `GameTab`, `Control` and `PackageRequirement`. `describe({ software, version, settings? })` resolves tabs, Action ids, widget ids, command control and runtime packages. Minecraft loader/version facts remain Minecraft-specific, not a required schema for future games.
- `src/games/art.ts` and `GameDefinition.art`: each game declares its poster (2:3) and banner (about 3:1) under `public/assets/games/<id>/`. `scripts/fetch-game-art.ts` downloads them once, with no credentials, and records the source URLs in `scripts/game-art-sources.json`; the panel never fetches art at runtime. The new-server picker (`GamePicker`) shows every registered game from this art; `add-server` takes the picked `game` id and throws for an unknown one.
- `src/games/index.ts`: bundled `games`, `gameFor(id)` and the new-server `defaultGame`. Unknown ids throw, including when deserializing stored servers. `assertGameAction` enforces resolved capabilities before a service Action executes.
- `src/games/serviceTypes.ts`: service-only `GameService`, `LaunchCommand`, `PreparedLaunch` and `PortSpec`. Hooks own initial state, options, launch preparation, mutation checks, stop/control, line observation, initialization, icons, disposal and backup consistency. `afterStop` runs once the server's process is gone however it went (stopped, crashed, killed, a launch that failed) and before a restart starts again: a game takes back what `prepareLaunch` set aside for the start, as Palworld does with the passwords it writes into its settings file. `src/games/service.ts` resolves these implementations using the current server's explicit id.
- `src/games/uiTypes.ts` and `ui.tsx`: bundled `GameUI.create` produces a per-view `GameView` for setup and game tab renderers separately from service code. App renders the resolved menu in order; Files, Logs and Backups are shared tabs. Minecraft's existing specialized components remain in `src/components`, owned through `minecraft/ui.tsx`.
- Shared game UI: a game does not copy screens, it fills these in. `components/GameRoster.tsx` is the Players tab of a game with no roster of its own: the game merges its players, says what Kick and Ban mean (`RosterModeration`), and adds sections and Details rows; `createRosterState` loads the roster and quotes a failed action with the player it failed for. `components/InstallProgressModal.tsx`, `InstallNotices.tsx` and `InstallStepView.tsx` are the Versions tab's progress and notices and the setup wizard's install step; `games/installFlow.ts` is the running, installed and error state under a game's install rows; `components/ServerOverview.tsx` (with `EditableDetail`) is every Overview. `PlayerAvatar` draws players of a game with no skins. `test/uiStandards.test.ts` fails a game that builds its own roster list, avatar or install rows.
- `src/games/minecraft/`: metadata in `index.ts`; service hooks in `service.ts`; launch in `launch.ts`; readiness, players/chat/gamerules/port observation and on-ready work in `observe.ts`; Java in `java.ts`; installers in `softwareInstall.ts` and `providers/`; Actions and options in `actions.ts` and `config.ts`; port files in `ports.ts`; save acknowledgment and crash recovery in `saving.ts`. Import these implementations directly from `src/games/minecraft/`; shared service infrastructure stays in `src/service/`.

Shared lifecycle owns process start/exit/restart, chunk buffering and force-kill timers. It receives a resolved executable, args, cwd and env; it does not construct Java commands or parse Minecraft output. Minecraft keeps its existing evidence-based readiness markers; this refactor does not introduce a new startup deadline or change their behavior. A new game's readiness adapter must provide a bounded, evidence-based failure path.

Modules yield `PortSpec`s in order, reading/writing their own files; `src/service/ports.ts` claims/prepares them through the Port API. Minecraft keeps `java` and `bedrock` claim identities and existing per-server prefixes. Linked allocation waits for the first game needing it (Valheim, a future candidate below); no selected game does.

Log viewing and command input are distinct; `Control` supports `none`, `stdin`, `rcon` and `broadcast`. Every console line passes `commandLine`, which refuses what the game must not take; `rcon` games then send what it returns through `GameService.sendCommand`. `serverLevel` is the map or level a running server plays, for games that change it while running. A game without a world passes `world={false}` to `ServerOverview` (Source derives it from its Actions), so the Overview has no Save world. Secret options can name what they hold with `noun` ("token") for their field. Players/moderation require a real roster adapter. Minecraft's quiesce backup policy retains save-off/save-all/save-on acknowledgments, cleanup on copy failure, and the pause marker across service restarts. An offline-only policy refuses live backup. Widgets stay declared in the manifest; choices and runtime rendering consult resolved support and unsupported selections fail visibly.

`PackageRequirement` describes runtime ids from the daemon Package API (Java today). Setup installs the required Java; launch verifies it. Future distribution, host support, options schemas, RCON/HTTP control and runtime runners belong to the first module actually using them, with no placeholder implementations. Minecraft's protected-data and install-file rules remain specific to Minecraft; a future module must define its own persistent-data boundary.

## Shared packages

| Resource | Where |
|---|---|
| Java, SteamCMD bootstrap | Daemon packages under `$PAPERBOARD_DIR/packages`, via `packageApi` |
| SteamCMD's mutable install/cache | A tool workspace under `$PAPERBOARD_DIR`, use serialized |
| Steam account session | Private workspace; credentials in the vault |
| Game binaries + Steam manifests | Per-server install directory |
| Saves, settings, mods, logs | Per-server persistent data, kept on uninstall |

SteamCMD adapter: verified per-platform bootstrap; `force_install_dir` before login; explicit target platform and branch; anonymous where possible and never silently retry with an account; Steam Guard as an interactive challenge, passwords/tokens in the vault, one-time codes never stored, output redacted; GSLTs, Klei tokens, RCON passwords as separate secrets; serialize SteamCMD and per-server mutations; verify success from output *and* files; stop the server before updates (`validate` can overwrite edited files); record app id, platform, branch, build id.

No planned game needs a Wine or Proton runner; the `proton` Origami package stays published for future Windows-only games. Wine translates APIs, not CPUs; Rosetta runs Mac Intel binaries, not Linux ones. Most Steam servers are x86-64 only. Unsupported OS/CPU combinations are marked unsupported, never implied to work.

## Implementation order

This is a plan, not implemented support. Keep Minecraft behavior and stored identities intact. Each phase ships a complete module with documentation and passing tests. Register a new choice in the UI only after the owner has joined its server; certify each host route independently. Uncertified routes remain unavailable with a reason, never an experimental choice.

| Phase | Delivery | Reason / exit condition |
|---|---|---|
| 1a | Terraria vanilla + the remaining generic seams | Small download, no SteamCMD, stdin console, publisher builds for all three OSes. Proves the boundary with a genuinely different game. |
| 1b | tModLoader as Terraria's `software: "tmodloader"` option | Reuses worlds/console/ports; proves versioned software variants without another game id. Separate join check from vanilla. |
| 2a | `steam` workspace + TF2 + Source RCON/A2S | TF2's dedicated download is smaller than CS2's combined client/server depot. Prove the Steam seam with SRCDS before Source 2. |
| 2b | CS2, then Garry's Mod | Share Steam and protocols, not launch/config assumptions. GMod Workshop waits for the modscan Workshop search (see Owner decisions). Each game ships independently. |
| 3 | Palworld, native Linux/Windows, REST administration | Reuses Steam installation; introduces typed HTTP operations. Current upstream deprecates RCON, so do not make it the primary adapter. |
| 4 | Rust, native Linux/Windows, WebRCON | Large download and memory; adds a WebSocket admin adapter (WebRCON is not Source RCON). Reuses the Steam seam; needs no linked ports or Proton. macOS stays unsupported. |

### Contract changes, introduced with their first consumer

Names below are proposed additions to the actual contracts, not claims about existing APIs. Keep game-specific values in their modules. Do not widen the global PaperAPI for one game.

**Phase 1 (`src/games/types.ts`):** retain `GameOptions { software, version, settings? }`; validate software/version in each module. Add `GameDefinition.hostSupport(host: { os: string; arch: string }, options: GameOptions): { supported: boolean; reason?: string }` for setup and service enforcement. Describe Rosetta as an explicit prerequisite, not native ARM support. Add `GameFeatures.options: readonly GameOption[]`, where `GameOption` is a discriminated union of `text`, `number` (min/max), `boolean`, `select` (value/label choices), and `secret`; common fields are `id`, `label`, `description?`, `restartRequired`, and an optional non-secret default. Secret fields expose only presence, never defaults or values. Schema metadata is UI-safe; module Actions validate and persist edits and preserve unknown config keys. Minecraft can expose its existing specialized editor with an empty generic schema; do not rewrite it just to fit this form.

**Phase 1 (`serviceTypes.ts`):** keep `LaunchCommand`'s executable/args/cwd/env and `PreparedLaunch` shape. Add optional `GameService.readiness: { timeoutMs: number; probe(ctx): Promise<boolean> }` (false means still starting, rejection means a visible startup failure); poll with no overlap, cancel on stop/exit/dispose, and enforce the deadline even if the process produces no output. New modules require it; Minecraft retains its existing markers. Add `stopTimeoutMs?: number` rather than imposing the current 15-second force-kill on world saves. Make `stop(): Promise<void>` so delivery failures reach Actions/UI; adapt Minecraft without changing its command. Keep `commandLine` and stdin for phase 1. Keep existing `backup.mode: "offline" | "quiesce"`; new games start with offline backups, not an unproven save acknowledgment treated as a write lock.

**Phase 1 (`uiTypes.ts`):** no new rendering abstraction. `GameUI.create`, `GameView.setup` and `tab`, plus existing `GameTab` descriptors, suffice; setup's software/version remain strings. Use PaperUI elements for each game's views. Add no custom shared visual component without discussing its need. Files/Logs/Backups stay shared; their service Actions must dispatch through each game's capabilities rather than Minecraft's protected-file rules.

**Phase 1 integration outside those types:** `GameServerState.serverSoftware`, `lib/server` and setup consumers still use Minecraft's `ServerSoftwareType`; make the common value a string and narrow only inside Minecraft. Add a secret-free `gameSettings` snapshot for `describe` and pass it at every Action/tab/widget capability check (currently callers omit `settings`). `add-server` takes the explicit game id chosen on the picker's first step and throws for an unknown or missing one before creating any files. Register matching metadata/service/UI implementations; unknown ids still throw. Move shared lifecycle/file/log Actions out of Minecraft ownership and collect module Action custom types instead of the root service importing only Minecraft's `customTypes`. Preserve all existing Minecraft ids and schemas. Give each module its own data-protection/install manifest; never feed Terraria through Minecraft's JAR installer or world/reset logic.

**Phase 2 (`types.ts`):** extend `Control` with `{ kind: "rcon" }` (transport capability, no endpoint or credential). Add `GameFeatures.distribution?: { kind: "steamcmd"; appId: number; platform: "linux" | "windows"; branch: string; login: "anonymous" }`. These selected servers need anonymous downloads, not a Steam password/Guard UI. Populate `packages` with existing `PackageRequirement { id: "steamcmd", purpose }`; do not add another package API or duplicate Origami definitions. Add `GameOptions.targetPlatform?: "linux" | "windows"` in this phase, supplied from validated host/runtime selection (required for Steam descriptions, optional for Minecraft). Pass it consistently to `describe`; never infer a Windows depot from a renderer OS. Metadata resolves that depot platform explicitly; service checks host support separately.

**Phase 2 (`serviceTypes.ts`):** replace lifecycle's unconditional `commandLine` → `processApi.write` path with required `GameService.executeCommand(ctx, command: string): Promise<string | void>`; Minecraft/Terraria keep their existing command validation/newline formatting inside this hook. RCON replies are displayed through the same bounded console log, with errors propagated. Route stop/chat through the module too. Single-line raw input remains enforced at the service boundary. Add optional `GameService.queryPlayers(ctx): Promise<PlayerSnapshot>` with `PlayerSnapshot { count: number; max: number | null; players: readonly { id?: string; name: string }[] | null }`; null roster means unavailable, not an empty server. Add corresponding nullable count/roster freshness to common state/widgets; Minecraft can adapt its existing observer without changing its polling. A2S counts cannot be derived from `onlinePlayers.length`. No RCON address/password in shared UI state.

**Phase 3:** extend `Control` with `{ kind: "http" }`. Keep `executeCommand` but expose Palworld's supported named operations through validated Actions, not an invented arbitrary REST console; only advertise a console widget if that command vocabulary is implemented. The REST client and endpoint mapping live in `games/palworld/`, not a global HTTP Action. `GameTab`, option schema, readiness, `queryPlayers` and `LaunchCommand` need no further changes.

**Phase 4:** extend `Control` with `{ kind: "webrcon" }` (transport capability, no endpoint or credential) and route it through `executeCommand` like phase 2's RCON. Rust's WebRCON is a WebSocket carrying JSON frames, authenticated by the password in the URL path, so the adapter keeps that URL out of logs, errors and state. Players come from `playerlist`, with count and cap under the same freshness rules as phase 2's `queryPlayers`; null means unavailable, not empty. Rust's ports (28015, 28016, 28017) are independent, so `PortSpec.linkedTo`, `LaunchCommand.processTree` and `PreparedLaunch.runtime` are not part of this plan. Add each with its first consumer: linked ports with Valheim, descendant supervision when a launch wrapper (tModLoader or a Steam wrapper) can outlive its parent, and a runtime runner with the first Windows-only game. Do not ship a leaking wrapper while waiting for one.

Port preparation currently happens **after** `prepareLaunch`. Before phase 2's CLI ports, load options/check mutation state, allocate/write all ports, then resolve launch args from those final values under the same per-server mutation exclusion. Do not launch with an old port after the registry moves it. Process scoping currently recognizes only `mc-server`/`mc-installer`; generalize using each module's declared `processIds` and a declared primary process id, preserving legacy Minecraft ids. Audit service listeners, backup process lists and restart/kill paths together.

### First-version game specifications

Commands below use install-relative paths; adapters resolve absolute executables and argument arrays, never interpolate user values into shell command strings. `P`, `Q`, `R` mean the allocated game, query and admin ports. Publisher scripts, if needed, are downloaded release artifacts, never fetched-and-piped scripts. Validate the pinned release's entrypoints and libraries before marking install complete.

**Terraria (`terraria`, software `vanilla` / `tmodloader`)**

- Vanilla source: publisher ZIP `https://terraria.org/api/download/pc-dedicated-server/terraria-server-<digits>.zip` (e.g. `1449` for 1.4.4.9). Resolve available releases from the publisher link, record version/source/archive digest, and reject missing releases rather than guessing a latest URL. Launch Linux `<version>/Linux/TerrariaServer.bin.x86_64 -config <absolute-config>`; Windows `<version>/Windows/TerrariaServer.exe -config <absolute-config>`; macOS `<version>/Mac/Terraria Server.app/Contents/MacOS/TerrariaServer -config <absolute-config>` (verify bundle path on the selected release).
- tModLoader: pinned stable GitHub release asset from `tModLoader/tModLoader` (size and SHA-256 in `terraria/catalog.ts`), not SteamCMD app 1281930. The release's launch scripts download .NET at launch, so they are not used: the service runs `dotnet tModLoader.dll -server -config <file> -nosteam -tmlsavedirectory <server>/tModLoader -noupnp` on Origami's `dotnet-<major>` package, installed at setup with the panel's package API. Its Terraria base is the first log line (`Starting tModLoader server <terraria>+<version>`), not vanilla latest. Mods, `enabled.json` and saves live under the server's `tModLoader/` folder, never the user's Documents.
- TCP P=7777 only. Generate `serverconfig.txt`: world path, autocreate size, world name/seed, difficulty, maxplayers, motd, port, password, secure/UPnP policy (UPnP off initially). Expose name, world select/create/import, size, seed, difficulty, player cap, MOTD, port, and join password; creation-only settings must say so. Vanilla and modded worlds stay separate; switching software requires stop and a compatible world selection, never an implicit conversion.
- Admin: stdin `help`, `say`, `kick`, `ban`, `save`, `exit`; parse real `playing` output plus join/leave events for roster. No A2S/RCON. Readiness requires the pinned build's listening/startup completion marker, bounded probe verifying its listener, and no interactive world-selection prompt. Port-open alone does not establish completed world generation.
- `save` waits for completion; graceful `exit` saves, then await actual exit (initial 120s stop budget). Backups are offline only: retain `.wld`, `.bak`, `.twld`, mod manifests/config, banlist and server configuration. Refuse live copy even after `save`; autosaves can resume. Keep data on update/uninstall, and migrate neither vanilla nor modded saves without explicit action. Terraria version updates may rewrite world formats; retain a pre-update offline backup.
- Tabs: Overview, Players, Worlds, Options, Versions, plus shared Files/Logs/Backups. tModLoader adds a Mods tab (Software group): the shared add-on browser over `tModLoader/Mods`, searched through modscan and downloaded by SteamCMD. Widgets: status, players, console; no Minecraft MOTD renderer/stats/map features.

**Team Fortress 2 (`team-fortress-2`), registered**

Built on `src/games/source/` (`sourceGame`, `sourceService`, `sourceUI` take a `SourceGameSpec`), which CS2 and GMod reuse where their servers match. What shipped, verified against the real build 26334371 on Linux:

- Launch: `stdbuf -oL -eL srcds_linux64 -game tf -console -ip 0.0.0.0 -port P +clientport C -nohltv +maxplayers N +sv_lan 0|1 +exec paperboard_secrets.cfg +map M`, `LD_LIBRARY_PATH=bin/linux64`, HOME in the server's `profile/` with `~/.steam/sdk64/steamclient.so` copied from SteamCMD. srcds holds its output in a buffer on a pipe (hence `stdbuf`), ignores stdin without a terminal (hence RCON), and binds RCON only on its detected LAN address unless given `-ip`.
- Preflight: `ldd` over the binary and its libraries; a missing system library (in practice `libcurl-gnutls.so.4`, absent on Arch, which makes `replay_srv.so` fail with a misleading "wrong ELF class") stops the start with the package to install.
- Config: `tf/cfg/server.cfg` and `banned_user.cfg` are generated from Options and Paperboard's ban list at each start and on change (`log on`, `sv_logecho 1`, `sv_rcon_whitelist_address 127.0.0.1`); the user's own `server.cfg` in the server folder runs last as `paperboard_user.cfg`. Passwords (RCON, join, GSLT) live in the vault and reach the server through a 0600 `paperboard_secrets.cfg` removed once it is ready. The install is read-only through Files.
- Control: RCON on the game port with a vault password Paperboard makes; readiness is an authenticated `status`; stop is RCON `quit` (30 s). Players, chat, joins/leaves, teams and map changes come from the HL log lines the console echoes. Bans are by Steam id, work while stopped, and go over RCON (`banid`/`removeid`) while running. The Overview changes map through a searchable picker of installed `.bsp` files, named by mode.
- Windows: `srcds_win64.exe` with the same arguments and `consoleInput` (see Windows below); SourceMod and Metamod come from Origami's `windows-x64` builds.
- Not yet: Workshop maps, SourceTV, a verified GSLT login (`sv_setsteamaccount` from the early `+exec` is untested without a token).

- UDP P=8211; local/private TCP REST=8212, enabled explicitly. Optional public/community query endpoint Q=27015 only if the selected build/mode actually binds it; verify rather than inherit an ASE/Source port list. RCON TCP 25575 is deprecated: disabled and unclaimed in v1.
- Edit `Pal/Saved/Config/{LinuxServer|WindowsServer}/PalWorldSettings.ini`, preserving unknown keys and INI escaping; `DefaultPalWorldSettings.ini` is only a template. Expose ServerName/Description, player cap, join/admin passwords, game/REST ports, visibility, allowed client platforms, difficulty presets and a small set of rates (XP, capture, day/night). `PublicPort` advertises NAT routing; it does not change the listener. Secrets are separate vault entries, including AdminPassword used by REST.
- REST Basic auth, local `/v1/api/info` readiness and `/v1/api/players` roster/count (retain platform ids and Unicode names). Typed Actions for announce/kick/ban/save/shutdown; no shell commands. Use REST Save then Shutdown with bounded wait, and await process exit (initial 120s budget). Offline-only backup of `Pal/Saved` including SaveGames, config and bans; successful Save response does not freeze world writes. REST errors/auth failures must be visible; restrict admin access locally with binding/firewall checks where the game cannot bind loopback.
- Tabs: Overview, Players, World Settings, Options, Versions and shared tabs; no v1 mods installer. Widgets: status and players; console only after a tested typed command adapter exists, otherwise Logs stays readable with no command input.

**Rust (`rust`)**

- SteamCMD app **258550** (dedicated server), anonymous, public branch; the Steam store/client app is 252490 and is the id for any client-facing link, not for the download. Linux `RustDedicated -batchmode -nographics +server.port P +rcon.port R +server.queryport Q +rcon.web 1 +server.identity <id> ...`; Windows `RustDedicated.exe` with the same arguments. Verify the entrypoint, the Linux library path (the server ships its own native libraries) and each argument against the installed build; build the argument array from validated values, never a shell string. No macOS dedicated build.
- Game UDP P=28015, query UDP Q=28017, WebRCON TCP R=28016: three independent endpoints, so no linked allocation. Claim all three through the Port API and pass the final values on the command line (see the port-preparation note above). Confirm the actual listeners after launch and refuse an advertised endpoint that does not match.
- Server data lives under the install's `server/<identity>/` (map, saves, `cfg/server.cfg`, `users.cfg`, `bans.cfg`). Expose hostname/description, player cap, map size and seed (creation-time; a procedural map is regenerated when either changes or on a forced wipe), save interval, RCON password and PvE/PvP-style presets. The RCON password is a vault secret: WebRCON puts it in the URL path, so redact it from process arguments, logs and errors, materialize it only for the launch and the adapter, and never show it in renderer state. Do not expose it on a public port.
- Readiness: the server's own startup-complete evidence plus an authenticated WebRCON round trip, with a configurable initial deadline for map generation and loading (a large first map takes minutes). Save and stop through WebRCON (`server.save`, then `quit`), await process exit (initial 120s stop budget); prove the save on the selected build, since an empty reply is not proof. Backups are offline only: retain `server/<identity>` (map, saves, config, user and ban lists) and the chosen identity, not the replaceable depot. Players from `playerlist`, with unavailable shown as unavailable.
- A forced wipe updates the game and the map; clients and servers must match builds, so Versions shows the installed build and an update is an explicit, stopped-server action. Mods are excluded from v1: uMod/Oxide and Carbon are server-side plugin frameworks installed into the server files, and they are not Workshop items.
- Tabs: Overview, Players (only with a verified `playerlist` adapter), Options, Versions and shared tabs. Widgets: status and console; players when the roster adapter passes. macOS unsupported. Large downloads and RAM make this the last phase.

### Windows

Terraria (vanilla and tModLoader), TF2 and Palworld were verified server-side on Windows 11 x64 on 2026-11-01: install, start, console commands, chat, save, offline backup, stop and restart. TF2 also covered map changes and SourceMod; tModLoader covered a Workshop mod. Client joins are still on the owner checklist. What differs from Linux:

- **Prerequisites:** Windows has no package manager the panel may drive, so a missing runtime stops the start with its download link (`src/games/windowsRuntime.ts`). Terraria needs XNA Framework 4.0, and Palworld needs the Visual C++ 2015–2022 x64 runtime (without it the server exits with 0xC0000135). tModLoader brings its own .NET from Origami.
- **Console input:** Terraria and tModLoader set `Console.InputEncoding` to Unicode on Windows, so their commands are written as UTF-16 (`inputEncoding: "utf16le"`). srcds in `-console` mode reads a real console and quits on a pipe, so it runs with `consoleInput` and Paperboard talks to it over RCON.
- **SteamCMD:** on Windows, SteamCMD that updates itself exits with 7 and runs the rest of the command in a child Paperboard can't watch. A `+quit` run takes the update first (`takeSelfUpdate`).
- **RCON readiness:** srcds drops a reply in flight while it bans someone else's bad RCON attempt, which an internet scanner makes. During startup a reply that never finishes means "not ready yet", not a failure.
- **Saved folders:** Palworld's `Pal/Saved` is a junction to the server folder's `saved/`, as on Linux it is a symlink.

### Shared implementation pieces

- **`src/games/steam/`:** use `packageApi.isInstalled/download/getPath` for `steamcmd`. Copy the bootstrap into a mutable tool workspace under `PAPERBOARD_DIR`; never run its self-updater in the shared package directory. Hold one cross-service workspace lock plus a per-server mutation lock (fixed lock order) across self-update/login/download/manifest read. Isolate Steam HOME/cache and SDK paths from the user's Steam installation. Track bootstrap package version and refresh only when no run holds the workspace.
- Run `force_install_dir <absolute-install>` before `login anonymous`, set target platform, then `app_update <appId> [-beta <explicit-branch>] [validate]`, then quit. Anonymous is expected for all five selected Steam apps; subscription/CDN failures are visible errors, never silent account fallback. Record app id, branch, depot platform, manifest build id and runtime version; don't promise Steam can reinstall any historic build id. Parse progress incrementally, retain a bounded redacted error tail, and require successful app output, manifest and executable checks, not exit code alone.
- Stop and verify all server processes exited before update/validate or file replacement. Preserve a recorded boundary between depot files and saves/config/mods; stage or journal updates and block launch after interruption until recovery settles. `validate` can overwrite customized depot files: protect user config, reapply module-generated config and report conflicts. Do not delete saves on uninstall. No invented download checksum: use publisher/Steam verification, record locally computed archive digests where useful.
- **`src/games/source/`:** TF2/GMod share SRCDS config helpers; CS2 has its own launcher. TCP Source RCON handles auth rejection, request ids, partial/multiple frames, multi-packet replies, UTF-8, bounds, timeouts/reconnect and shutdown EOF. Reject command injection/newlines and redact credentials/secret-changing commands before logs. Reuse protocol framing for ASA only after testing its dialect. Raw RCON is not encrypted; use loopback/admin-network access and do not advertise admin ports for public forwarding.
- **A2S client:** UDP INFO for counts/map/cap, PLAYER for names where supported; implement challenge retry, split/compressed packet handling with strict size/deadline limits. Poll locally with no overlap; dispose timers/sockets on stop/removal. A2S names are not stable Steam identities; use RCON status for moderation and never invent UUIDs or mark a stale query as zero players.
- **`src/games/webrcon/` (Rust):** a WebSocket client for WebRCON: authenticate through the URL path, send JSON `{ Identifier, Message, Name }`, and match replies by `Identifier` (the server also pushes unrelated console lines on the same socket). Bound frame size and reply time, reconnect visibly, close on stop/removal and never leave a socket or timer behind. The URL contains the password: build it at the last moment, keep it out of every log, error and state object, and redact it in diagnostics. Unencrypted: loopback/admin-network access only, never advertise the port for public forwarding.
- **Secrets:** `secretsApi` in `packages/paperapi/src/secrets.ts`, scoped by explicit panel id and keys containing server id (join password, admin/RCON password, GSLT independently). Ordinary settings hold secret presence/references only. Materialize required plaintext game config with restrictive file permissions/Windows ACLs and redact console/process diagnostics. Omit secrets from ordinary exports and backup config where possible; when a game's required INI contains credentials, treat that backup as sensitive and document re-entry/rotation on restore. Never duplicate secrets into renderer state, Action output or install records.

### Owner decisions

Decided by the owner on 2026-10-30:

1. Certification machines: Linux x64 (this Arch host), Windows x64 laptop and Intel Mac. Apple Silicon has no test machine; it remains unsupported with an explicit reason until certified. Do not ship a Rosetta route based on inference. Windows x64 and Intel Mac stay blocked in setup/service until their independent certification passes. Linux's real-server smoke test does not replace the owner's client join; complete the join checklist before release.
2. Offline backups are acceptable, including schedules: announce when supported → save → graceful stop and verify process exit → copy → restart if previously running. Full named-source Backup API integration is required: separate history and schedules per server, local/Google Drive/S3 destinations, restore with stop-before-replacement and restart, and retention. Terraria uses that existing API rather than a second backup system. Its resume marker lives outside its source so restored settings cannot request a restart. The SDK's generic `beforeRestore` hook prepares owned processes before the daemon replaces files.
3. Mods come only through a search/download API comparable to Modrinth. tModLoader's Mods tab is the first: Workshop search and item lookups go through the modscan worker (`apps/panelapis`, `panels.ariapis.com/modscan`), so the panel never holds a Steam Web API key, and every result list shows Valve's attribution, disclaimer and legal notice from modscan's `meta`. Files come from SteamCMD (Origami's `steamcmd`, copied into the panel's `.steam` workspace and run anonymously, one run at a time); the newest build folder not newer than the server's tModLoader is copied into `tModLoader/Mods`. Required items are followed through each item's Workshop children, and each `.tmod`'s own `modReferences` are checked before anything is placed, all or nothing. Still excluded: GMod Workshop and Rust plugins. Other approaches, once they exist:
   - Import from the user's local Steam install: subscribed Workshop items and tModLoader's `enabled.json`.
   - Pasting Workshop links or ids, resolved through modscan.
4. ARK: Survival Ascended was dropped from the plan as too troublesome; Rust (SteamCMD 258550) replaced it as the last phase. Proton is no longer part of the first-games plan; the `proton` Origami package stays published for future Windows-only games.
